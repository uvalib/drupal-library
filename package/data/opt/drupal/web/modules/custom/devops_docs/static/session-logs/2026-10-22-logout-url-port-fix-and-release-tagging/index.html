    Session Log: Logout redirect to https://host:80/ — hot fix, pairing git and docker tags, a path-filtered pipeline trigger, and the production rollout with a theme promotion

    Date: 2026-10-22 (about 10:55 ET to just after noon; times approximate) Participants: Yuji Shinozaki, Claude (Sonnet 5.5), working from the drupal-library repo Outcome: Production (both nodes) now runs drupal-library:build-20261022153610 (417b835, git tag production_2026_10_22), NetBadge build-20261022034941 (unchanged) and theme prod-theme-20261022-login-form-fixes (e24e27bc). The logout fix is now in the image, not just hand-applied; logout was confirmed working on staging and prod (before the rollout, with the hand-edit). The staging pipeline no longer builds/deploys on docs-only merges (trigger_paths, applied and proven by a docs-only push that started nothing). Develop was deployed afterwards (section 12). The two prod nodes were compared after the rollout and are identical (section 10).

    Session also began with "pull and update" (see section 5).

    1. Cause

    The bad URL was not the logout link (/user/logout redirects correctly) but the place SimpleSAMLphp sends the user after logout.

    • logout_goto_url is empty on staging, so simplesamlphp_auth_user_logout() calls Auth\Simple::logout(null).
    • With no return URL, SimpleSAMLphp builds one with Utils\HTTP::getSelfURL(), whose getServerPort() reads $_SERVER['SERVER_PORT'] and appends :<port> unless it equals the default for the scheme.
    • HTTPS terminates at the ALB, so SERVER_PORT is 80 inside the container, while the Apache vhost sets HTTPS=on from X-Forwarded-Proto. Scheme https + port 80 gives https://host:80/.

    Which container. The user asked whether this was the NetBadge container or Drupal. The SimpleSAMLphp library code runs in the Drupal container (docker exec drupal-0 shows its own /var/simplesamlphp/config); netbadge-0 only receives the ReturnTo that Drupal already got wrong. "NetBadge" is SimpleSAMLphp, so it is fair to call this a NetBadge-stack limitation, but redeploying the netbadge-0 image would not change it. I did not rule out that the sp container has its own :80 problem on its logout endpoint; staging and prod behaved correctly after the Drupal-side fix, so it evidently does not matter.

    Affects every environment behind the ALB. The user reported prod and staging; develop was not checked.

    2. Options weighed

    Option Verdict
    drush cset simplesamlphp_auth.settings logout_goto_url https://<host>/ No redeploy, one command for both prod nodes (config is in the DB), trivially revertable. But hardcodes a URL per environment, and develop's weekly prod DB clone would carry prod's URL into develop. Not applied.
    Fix in the NetBadge container Rejected: the wrong value is made in Drupal's process, so the NetBadge side would be rewriting it.
    Hand-edit settings.php in the container, then redeploy later Chosen (the user wanted no redeploy right now). Environment-agnostic; the same code ships in the image. Risk is a syntax error taking the site down, mitigated by backup and php -l.

    3. The fix

    package/data/opt/drupal/web/sites/default/settings.php, +13 lines after the reverse_proxy_* settings:

    if (($_SERVER['HTTP_X_FORWARDED_PROTO'] ?? '') === 'https'
  && \Symfony\Component\HttpFoundation\IpUtils::checkIp($_SERVER['REMOTE_ADDR'] ?? '', $settings['reverse_proxy_addresses'])) {
  $_SERVER['SERVER_PORT'] = '443';
}

    Design point, from the user: "I shouldn't use $_SERVER['SERVER_PORT'] blindly." The first version trusted X-Forwarded-Proto unconditionally. It was tightened to also require REMOTE_ADDR to be inside reverse_proxy_addresses (the VPC CIDRs), so a direct hit on :8080 from the VPN cannot spoof it. Only generated URLs are affected either way, so the risk was low, but the check is cheap.

    4. Rollout

    Each node: verified the live settings.php matched the repo HEAD version (md5), copied the new file in as settings.php.new, php -l, backed up as settings.php.bak-logout-port-20261022, mv into place preserving ownership/mode. Opcache has validate_timestamps=1, revalidate_freq=60, so no Apache restart. Staging first (user tested logout: works), then prod node 0 (health check), then node 1. The user confirmed logout works on prod.

    Shipped as PR #16 (merged by a teammate at 11:35 ET). The merge replaced the hand-edit on staging with the identical file; the backup files disappeared with the recreated container.

    5. Pull and update (start of the session)

    git pull --ff-only took main to d603eb9 (the PHP 8.4.27 / core 10.6.19 rollout). ddev composer install then failed twice with failed to CreateOrResumeMutagenSync; ddev mutagen reset plus ddev start fixed it, after which composer install, drush updb (nothing pending) and drush cr succeeded. core:requirements still shows stale local entity-definition mismatches and cron not run for months, which is normal for the idle local DB.

    Gotchas: drush updb -y auto-answers "yes" to a failing requirements check, so read it rather than trusting -y; drush core:requirements --severity=2 crashes on a colour bug, use --format=json.

    6. Tagging: git and docker did not agree

    The user asked for "a new production tag". Findings:

    • The newest git tag was production_2026_06_04 (a455c54), 71 commits behind prod. Git tagging had lapsed; releases were being tracked only by the ECR image tag.
    • Prod ran build-20261022134259. ECR shows it carries gitcommit-bc73b101…, i.e. PR #14. The build started 12 s after #14 merged, which is how it was inferred before ECR was checked.
    • The release branch is at 4079ce3 (July). Images are built from main, not from release, so CLAUDE.md's "main -> release via PR" no longer matches reality. The user left it as an open question whether to use release at all. CLAUDE.md was not edited.
    • build-20261022153610 carries gitcommit-417b8350…, so the git tag went on 417b835.

    Only functional diff between prod's running commit (bc73b10) and 417b835: the 13 lines in settings.php. The other changed files are docs. Also confirmed live: composer.json, composer.lock, php.ini and the Apache vhost on both prod nodes match the repo. (A first "mismatch" on php.ini-production was my error: the Dockerfile copies that file to php.ini.)

    Created and pushed annotated tag production_2026_10_22 on 417b835; the message records the docker tag, the gitcommit- tag, the previous prod image and the delta.

    Standard decided by the user (saved to memory): every production release gets both a git tag and a docker tag that agree; read the commit from ECR's gitcommit-<sha> tag rather than inferring it; for a second tag on the same day, add a letter suffix (_b, _c, …) rather than a number, so it cannot be mistaken for a time. The first tag of the day stays unsuffixed.

    AWS access: aws-vault exec staging --prompt=osascript -- aws ecr describe-images … (the user authorised it; read-only calls only).

    7. Stop deploying on docs-only merges (trigger_paths)

    The user's point: the deploy trigger should treat document updates as exceptions, as was done for mandala-navina (its pipeline got trigger_paths on 2026-07-16 and a docs-only merge then left the pipeline idle). Before this, every push to main, including docs PRs like #15, rebuilt the image and redeployed staging.

    Where it lives. Not in this repo: terraform-infrastructure/aws_cicd/pipelines/drupal-library/codepipeline.tf (the staging pipeline uva-drupal-library-codepipeline). It set no trigger_paths, so the module's optional trigger block was never emitted. Two sibling pipelines exist: drupal-library-release (watches release, now stale) and drupal-library-production-deploy (deploy phase only, source_branch default main); neither was changed, and it was not checked whether the production-deploy pipeline has recent executions.

    Change (+15 lines incl. comment, commit f49d1e5a8 pushed straight to master):

    source_artifact_format = "CODEBUILD_CLONE_REF"
trigger_paths = [
  "package/**",
  "pipeline/**",
]

    CODEBUILD_CLONE_REF is required by the path trigger (same pattern as mandala-drupal, cs-proxy, web-components, cdn-reporter). The paths are what feeds the image: package/Dockerfile copies only from package/, and pipeline/ holds the buildspec and deployspec. docs/, scripts/, mkdocs/ and README.md never reach the image.

    Gotcha. The rebuilt devops-docs site lives under package/data/opt/drupal/web/modules/custom/devops_docs/static/, and the Dockerfile git clones this whole repo at build time and symlinks that module. So regenerating the static site still triggers a deploy (which is what publishes /devops-docs), while markdown-only docs/ changes do not.

    Process. - terraform-infrastructure changes often and the user's checkout was parked on someone's feature branch (dsf-production-enable-matomo). So: fetch first, branch off origin/master, commit, push HEAD:master (the user said that repo does not use PRs for small changes), switch back and delete the temporary branch. - The edit is outside the library.virginia.edu/ subdirectory that was the previous edit scope; the user granted permission for this. - Plan and apply ran from a temporary worktree at origin/master, with aws-vault exec staging --prompt=osascript. main.tf passes access_key/secret_key with no session token, so the aws-vault temporary credentials failed with InvalidClientTokenId; setting TF_VAR_access_key="" and TF_VAR_secret_key="" made the provider use the normal credential chain. State is S3 (uvalib-terraform-state). - First plan (read-only, -lock=false): 0 to add, 1 to change, 0 to destroy. The user then asked for plan -out plus apply; the script applied only if the new plan was exactly that single in-place change to module.codepipeline.aws_codepipeline.codepipeline. It was, and Apply complete! Resources: 0 added, 1 changed, 0 destroyed.

    Verified live (aws codepipeline get-pipeline): trigger on branch main, file paths package/** and pipeline/**, source OutputArtifactFormat is CODEBUILD_CLONE_REF. No extra execution fired from the apply (newest remained the 11:35 ET run for 417b835).

    Effect on tagging. With docs merges no longer building, main's head can be newer than the commit in the latest image. The tagging standard already says to tag the commit in the image's gitcommit-<sha>, not main's head, so it holds, and it will now more often be that the two differ.

Last common commit 8f08bfa2 (2025-11-20); release took main once more on 2025-11-21 (PR #31); the first release-only content is 1431a415 (2025-11-11, a "Revert list config" commit made on the staging host). Of the six release-only commits only that one has content of its own; the rest are merges. I first said tagging main would drop "the NetBadge login work"; that was wrong (the login work is on main via a different merge).

    • Theme repo PR #34 (branch release-login-form-fixes) merged with a merge commit (e24e27bc), tag prod-theme-20261022-login-form-fixes (lightweight, like the existing ones) pushed. Pushing needed the scratch clone switched to an SSH remote (the HTTPS remote had no credentials).

    9. Production rollout (silent, no maintenance mode, no drush cr)

    Answering "can we do it silently?": yes. The only functional difference from what prod ran (bc73b10) was settings.php, which prod already had by hand-edit; the runbook says roll nodes without drush cr for a code-only swap; maintenance mode makes / 503, which the ALB health check will not accept, so both nodes would go unhealthy in about 4 minutes. Pre-flight: both nodes healthy, maintenance mode 0, both on the same theme tag as the SSM pin.

    1. SSM pin /themes/uvalib/drupal-library/release set to prod-theme-20261022-login-form-fixes (v9; prior v8).
    2. Node 1: drain (alb-state drupal-prod --remove ... --watch), deploy_backend.yml -e deploy_tag=build-20261022153610 --limit uva-library-drupal-production-1 (failed=0), verified directly on :8080 (200s, image, theme tag, settings.php checksum from the image, maintenance 0), re-added and waited for healthy. Then node 0 the same way.
    3. Permission gotcha: the first alb-state drain was blocked by Claude Code's auto-mode classifier (no explanation). I did not work around it; the user added a Bash permission rule for it, after which it ran.
    4. After: ALB both healthy; the public site returned 200 repeatedly; /user/login 200; /saml_login 303 to the IdP; no error-level watchdog entries on either node. The user was asked to test a login and logout on prod.

    10. Post-rollout comparison of the two nodes and sessions

    • Config parity: a hashed fingerprint of each node (containers, mounts, ports, 45 env vars by hash, file hashes for settings.php, vhost, php.ini, composer files, SAML config, directory trees, theme commit, PHP modules, effective ini values) differed only in HOST_IP, ANSIBLE_HOSTNAME and free memory. Both are PHP 8.4.27.
    • Sessions are not per-node. Drupal sessions live in the shared database (10 rows, all authenticated, 2 active in 30 min); SimpleSAMLphp sessions live in the shared Valkey cluster (db 8, prefix SIMPLESAML_LIBRARY_PROD:, set by an environment variable, not the config default): 12 sessions plus 12 logout-store entries, the oldest about 5 hours old, so they survived both container swaps. 17 further keys in that db belong to another app (SIMPLESAML_DSF_PROD).
    • Traffic (10 min): node 0 694 requests, node 1 6,595, no 5xx on either. Node 0 had been re-added only ~5 minutes earlier (ALB ramp-up), so the skew is expected to even out; not re-checked. A direct established-connection count read 0 on both nodes and was discarded as unreliable.

    12. Develop

    • What it was: build-20261022134259, old settings.php, theme main HEAD, behind alb-library-drupal-develop (target group :8080) with the same vhost as prod and an empty logout_goto_url. The user reported "everything works" there. Simulating SimpleSAMLphp's getSelfURL() in its container with ALB-style inputs (https, port 80) produced https://<host>:80/, i.e. the bug is present in the code path. The 13:08 ET develop logout that worked was a GET /user/logout followed directly by GET / with no /simplesaml/ request, i.e. a non-SAML (local) session: simplesamlphp_auth_user_logout() only calls SimpleSAMLphp when isAuthenticated(). So that test could not show the bug. A real NetBadge logout on develop was not tested before the fix.
    • Deploy (user asked): library.virginia.edu/develop/ansible/deploy_backend.yml -e deploy_tag=build-20261022153610 (latest resolved to the same build; explicit pin so a newer build could not slip in). The playbook recreates the container and runs composer install, drush en simplesamlphp_auth, drush cr, an Apache reload and drush cim --partial of the SimpleSAMLphp config. failed=0. No ALB drain (single node, dev).
    • Verified: image build-20261022153610, settings.php checksum a9af532f (same as prod/staging), maintenance off, bootstrap successful, PHP 8.4.27, / and /user/login 200, /saml_login 303. Theme unchanged (main HEAD 9e2201de; the dev playbook has no theme step). With the deployed settings.php, the self-URL from an ALB-range address is https://<host>/, and from outside the proxy ranges it is still :80 (intended).
    • Confirmed by the user after the deploy: a NetBadge login and logout on develop worked, so the fix is verified end-to-end on develop, staging and production.
